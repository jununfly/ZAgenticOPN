# WorkBuddy task-agnostic activation routing validation

## Classification

`observed-failure`: the previous WorkBuddy activation read ZInitiatives
navigation context but produced no `discover` or `claim` event in the
ZAgenticOPN shared store.

## Minimal correction

Added `scripts/activate_agent.py` as the explicit Agent integration entrypoint.
It accepts only the Agent profile, scope and activation session; it has no
Work Item id argument. One invocation performs one `discover`, claims at most
one eligible execution or review item, and returns structured JSON. It does
not poll, wake agents, retry, or schedule work.

## Black-box evidence

| Scenario | Result | Observation |
| --- | --- | --- |
| WorkBuddy execution activation | PASS | External subprocess discovered and claimed `activation-c1` without a Work Item id. |
| Codex review activation | PASS | External subprocess discovered and claimed the awaiting-review frontier without copied context. |
| Same-device smoke | PASS | Codex → WorkBuddy → Codex ended in `completed`; both agent activations used the entrypoint. |
| Full tests | PASS | 9/9 unittest cases passed. |

The AgentRQ adapter remains a transport-only concern. Eligibility, atomic
claim and review state remain owned by ZAgenticOPN.

## Evidence boundary

This validates the project-local activation seam and its subprocess behavior.
It does not yet count as a real WorkBuddy UI/runtime experiment or as one of
the three consecutive value experiments required by the Experience Version
Spec. Human must rerun WorkBuddy with the repository activation instruction
before that evidence can be promoted.
