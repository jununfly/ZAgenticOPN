## 固定源码观察

### 产品形态与集成表面

1. AgentRQ is a human-agent collaboration platform organized around user-scoped workspaces and tasks. The README describes a Go/Fiber REST API, per-workspace MCP server, global CoreMCP supervisor, GORM persistence, SQLite/Postgres options, Google OAuth2/JWT authentication, and an internal event bus for SSE notifications (`README.md:104-116`).
2. The workspace MCP server exposes `createTask`, `updateTaskStatus`, `reply`, `getWorkspace`, `getTask`, `downloadAttachment`, and `publishEvent`; `getTask` without a task ID is explicitly described as returning the next `notstarted` task assigned to `agent` (`README.md:208-216`, `backend/internal/controller/mcp/server.go:309-343`, `backend/internal/controller/mcp/server.go:967-1039`).
3. AgentRQ documents a Codex gateway that bridges its MCP endpoint to the Codex app-server, with separate project-level `.codex/config.toml` and gateway `.mcp.json` responsibilities (`README.md:243-313`). It also documents an ACP gateway for other ACP agents and per-workspace MCP endpoints (`README.md:218-241`).
4. The source includes a DeepSeek Harness plugin that bridges the workspace tools and routes pushed tasks, human replies, reconnects, and per-task sessions. It uses one profile per workspace and carries a workspace URL/token (`plugins/deepseek-harness/README.md:1-33`, `plugins/deepseek-harness/README.md:72-121`, `plugins/deepseek-harness/README.md:125-181`).
5. The repository is Apache-2.0 licensed (`LICENSE:1-9`). The backend declares Go 1.25 and the MCP SDK, Fiber, GORM, SQLite and Postgres dependencies (`backend/go.mod:1-25`).

### R5：发现 shared frontier

**Unit capability: native. Full product requirement: unknown.**

- The persistence query selects one task by `workspace_id`, `user_id`, `status='notstarted'`, and `assignee='agent'`, ordered by `sort_order`/creation time (`backend/internal/repository/base/repository.go:325-345`).
- The MCP tool calls this query when `taskId` is omitted and returns `no pending tasks exist` when the query finds nothing (`backend/internal/controller/mcp/server.go:967-1000`).
- The MCP server also has a 60-second `StartPoller` that pushes the next pending task when no task is ongoing (`backend/internal/controller/mcp/server.go:500-571`). Human-created tasks can also trigger an immediate channel notification (`backend/internal/handler/api/task.go:81-127`).

This proves a queue/dequeue surface, not the ZAgenticOPN requirement that a Human activates an Agent with only “check shared context”, the Agent independently selects one eligible Work Item, and no automatic discovery is involved. The poller and push model also crosses a current Deferred boundary if adopted wholesale.

### R6：原子 claim 与唯一执行权

**Status: unknown; the source contains a material conformance risk.**

- `GetNextTask` only reads the next `notstarted` task; it does not update status, store a claimant, or execute a transaction with a state transition (`backend/internal/repository/base/repository.go:325-345`).
- The Agent is instructed to call `updateTaskStatus` separately to set the task to `ongoing` (`backend/internal/controller/mcp/server.go:281-303`). The app wiring also performs a separate read, status assignment, message insert, and `Save` (`backend/internal/app/app.go:342-406`).
- The implementation rejects a second `ongoing` task by listing existing tasks before saving, but that check and the write are separate (`backend/internal/controller/crud/task.go:305-363`). The source does not establish that two concurrent Agents cannot both pass the check or both execute the same task.
- The domain model has `Assignee` values `human|agent` and status values, but no persisted AgentInstance/claim record or lease field (`backend/internal/data/model/model.go:26-73`). MCP client identity is recorded for telemetry lookup, not as a task claimant (`backend/internal/data/model/model.go:181-199`, `backend/internal/controller/mcp/client_identity.go:11-73`).

Accordingly, AgentRQ should not be marked as passing ZAgenticOPN R6 without a reproducible competing-claim test. The correct label is `unknown`, not `absent`; the implementation seam is a high-priority risk if considered for reuse.

### R8：另一 Agent 的 review/next-work 接续

**Status: unknown for the ZAgenticOPN semantic; native only for Agent↔Human task messaging.**

- `reply` creates a task-thread message and routes it to the connected MCP session; the source documentation frames it as the only thing a remote human sees (`backend/internal/controller/mcp/server.go:762-800`, `backend/internal/controller/mcp/server.go:281-303`).
- `getTask(includeConversation=true)` can read a task’s message history, with cursor/limit pagination (`backend/internal/controller/mcp/server.go:967-1085`).
- Named events and workflows can fan out new `notstarted` tasks to subscribed workspaces, and the agent is instructed to publish events explicitly (`backend/internal/controller/event/event.go:88-209`, `backend/internal/controller/mcp/server.go:871-927`).
- None of these source paths establishes an `awaiting-review` state, a reviewer Agent role, reviewer claim, or a structured result/next-action contract owned by another Agent. Event/workflow fan-out is a different orchestration semantic and would import additional platform responsibility.

The most defensible status is `adapted` for message/event transport and `unknown` for the full R8 continuation gate.

### Scope, identity, provenance and safety

- Workspace and task records are user-scoped; each workspace MCP server is constructed with a workspace ID and owner ID, and task queries use both workspace and user ID (`backend/internal/app/app.go:304-340`, `backend/internal/repository/base/repository.go:213-226`).
- MCP sessions receive per-workspace connections and client identity can be hashed into telemetry, but the persisted task model does not separate Human, device, AgentInstance and session as ZAgenticOPN does (`backend/internal/controller/mcp/server.go:86-137`, `backend/internal/controller/mcp/client_identity.go:15-73`).
- Permission requests, auto-allow rules, task-level `AllowAllCommands`, tool-call records, and Human verdicts are implemented (`backend/internal/controller/mcp/server.go:1161-1253`, `backend/internal/controller/mcp/server.go:1310-1333`, `backend/internal/controller/mcp/server.go:1361-1440`). These are useful security/approval seams, but they are not a substitute for ZAgenticOPN’s provenance and claim semantics.
- README/docker configuration requires OAuth credentials, JWT/workspace token keys, persistent storage and optional Postgres/TLS/Slack operations (`README.md:121-154`, `docker-compose.yml:1-84`). Those responsibilities are disproportionate to the current same-device Experience Version unless a specific integration experiment needs them.

## Decision implication

The candidate is worth retaining as a **targeted C-route selective-reuse candidate**, not as a reason to reopen and rerun every old project immediately, and not as an A/B whole-product base.

The most promising follow-up is a narrow adapter/conformance experiment around the MCP workspace endpoint and the Codex/ACP integration seams. That experiment must first answer:

1. Can an activation adapter invoke a task-agnostic “get next eligible task” operation exactly once for the active Agent?
2. Can two concurrent consumers produce only one effective claimant and one execution, or does AgentRQ need a wrapper-owned atomic claim record?
3. Can a second Agent receive a structured result/next action and continue review without Human copying context?
4. Can the same-device single-project slice disable or avoid AgentRQ’s poller, scheduler, workflow fan-out, OAuth/deployment and cross-workspace supervisor responsibilities?

Until those tests pass, preserve ZAgenticOPN ownership of Work Item eligibility, Claim, result/review transitions, scope, private context, Git provenance and lifecycle gates. This targeted investigation is classified as `observed-failure` because it addresses the current activation/claim integration failure; it does not authorize production integration or a roadmap reopen.

## Research conclusion

- Re-running all previous open-source projects now is **not justified** by the current stage: the existing comparison gate has healthy receipts and the active blocker is Agent integration/routing, not an evidence gap in the chosen C route.
- A targeted AgentRQ study **is justified** because it is a new, unusually close candidate for the observed integration failure and exposes direct MCP/Codex/ACP seams.
- AgentRQ currently supplies credible queue, messaging, event, permission and gateway units. It does **not** yet provide evidence for ZAgenticOPN’s atomic claim or reviewer-Agent continuation semantics.
- The technical-c4 report now has a healthy receipt, but it should not be misread as a conformance pass: its seven sealed records are discovery evidence, while the pinned code studies carry the deeper implementation facts. A bounded black-box C1/C2/C4 fixture is still required before choosing a reusable adapter or unit capability.
