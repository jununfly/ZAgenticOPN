# 与 qm 方向相近的 GitHub 开源项目全景比较

## 1. Executive summary
qm 应继续作为产品形态 benchmark，而不是被 Stars 排名替代。当前最有价值的视角不是寻找一个“更好的 qm”，而是把候选拆成四类：OpenHands 代表可交付的 coding-agent 产品面，Goose 代表本地可扩展执行 harness，LangGraph/AutoGen/CrewAI 代表状态与编排底座，TaskWeaver 与 Aider 代表专业任务和极简 UX 单位能力。基于本轮固定 commit 的证据，暂不推荐整体复用任何候选；下一步应围绕 scope、sandbox、durable context、后台工作和 extension seams 做同一组黑盒 conformance，并以单位能力组合而不是产品搬运作为技术路线。

- 当前不推荐整体复用任何候选；推荐 C/D 混合：保留 qm-like 用户需求和产品语义为事实源，先补证据，再以单位能力选择性组合。
- 第一优先对 OpenHands 做产品面 conformance：scope isolation、conversation handoff、skills grant、sandbox/credential boundary、multi-device identity、background work 和 operator recovery。
- 第二优先研究 Goose 的 MCP、desktop/CLI、provider、sandbox 与 upstream workflow；只在其接口可被 ZAgenticOPN 或未来 base 以窄 adapter 包住时吸收。
- 把 LangGraph checkpoint/SDK 作为 durable state 与恢复的专项对照，把 AutoGen/CrewAI 作为 delegation/role orchestration 对照；不要把它们直接升级为完整工作产品。
- 把 TaskWeaver 的 chat/code/in-memory history 与插件函数作为专业任务单位能力实验，把 Aider 的低摩擦 coding UX 作为 Human intervention reduction 对照。
- 不复用 letta-ai/letta 当前 main 或 archive；若记忆能力仍是需求，应把 letta-code 作为独立的新候选重新固定版本并按同一标准采集。
- OpenCode、AutoGPT、AgentScope、Pydantic AI 先进入 fog/unverified 队列；下一轮优先补 canonical README、核心状态模型、部署、安全和可运行示例。
- 无论后续选择何种单位能力，都应保持 qm-like 的 scope、identity、durable context、human control、audit 与退出条件在自有 base 中定义；候选只能通过 conformance fixture 进入。

## 2. Key findings
- 本轮 qm 的直接 sealed evidence 主要是 AGENTS.md 维护与测试规约，不能独立证明完整多人产品闭环；qm 产品形态应作为 benchmark 继续用 canonical README、部署文档和黑盒场景验证。 [[1]](https://github.com/yc-software/qm/blob/568252bd4e6da5288b239573abef972f3e16b3f9/AGENTS.md) [[2]](https://github.com/yc-software/qm/blob/568252bd4e6da5288b239573abef972f3e16b3f9/AGENTS.md)
- OpenHands 证据显示前端通过 typed client 访问 agent-server 的 conversation、event、git 和 skills 服务，并存在 LLM/provider、settings、Cloud/device、skills catalog、telemetry 与 CI 表面。 [[3]](https://github.com/OpenHands/OpenHands/blob/7a9aacb7b69eef80c15f49230e27bbd2b3c6f41a/AGENTS.md) [[4]](https://github.com/OpenHands/OpenHands/blob/7a9aacb7b69eef80c15f49230e27bbd2b3c6f41a/AGENTS.md) [[5]](https://github.com/OpenHands/OpenHands/blob/7a9aacb7b69eef80c15f49230e27bbd2b3c6f41a/AGENTS.md) [[6]](https://github.com/OpenHands/OpenHands/blob/7a9aacb7b69eef80c15f49230e27bbd2b3c6f41a/AGENTS.md) [[7]](https://github.com/OpenHands/OpenHands/blob/7a9aacb7b69eef80c15f49230e27bbd2b3c6f41a/AGENTS.md)
- OpenHands 的本轮证据更接近 coding-agent 产品面；它是否覆盖 qm 的组织 scope、Slack/web 同身份、后台 cron/watch/webhook 和多租户权限仍未验证。 [[5]](https://github.com/OpenHands/OpenHands/blob/7a9aacb7b69eef80c15f49230e27bbd2b3c6f41a/AGENTS.md) [[6]](https://github.com/OpenHands/OpenHands/blob/7a9aacb7b69eef80c15f49230e27bbd2b3c6f41a/AGENTS.md)
- Goose 的仓库规约把它定义为 Rust agent framework，并维护 CLI、Electron desktop、devcontainer、MCP integration test 和 issue-driven upstream workflow；它适合执行与扩展单位能力参考。 [[8]](https://github.com/aaif-goose/goose/blob/cd23a1ed409eed6405da0b521af42186eaa32336/.devcontainer/Dockerfile) [[9]](https://github.com/aaif-goose/goose/blob/cd23a1ed409eed6405da0b521af42186eaa32336/.devcontainer/Dockerfile) [[11]](https://github.com/aaif-goose/goose/blob/cd23a1ed409eed6405da0b521af42186eaa32336/AGENTS.md) [[10]](https://github.com/aaif-goose/goose/blob/cd23a1ed409eed6405da0b521af42186eaa32336/AGENTS.md)
- Aider 的 README 将产品定位为与 LLM 结对编程，并强调云端和本地 LLM 接入；这使它更适合作为极简 coding UX 与 provider seam 参照，而非多人工作平台。 [[13]](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/README.md) [[14]](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/README.md) [[15]](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/README.md)

## 3. Analysis & synthesis
### role-families
qm-like 方向不是一个单一产品类别：OpenHands 更接近可交付工作产品，Goose/Aider 更接近执行 harness，LangGraph/AutoGen/CrewAI 更接近编排底座，TaskWeaver 是专业任务产品，Letta 是当前仓库不可直接复用的记忆方向。

### product-proximity
若目标是复刻 qm 的用户体验和组织协作，OpenHands 是最值得做产品面 conformance 的候选；但现有证据仍缺少 qm 的 scope/Slack/web/background 交叉闭环，不能判 A。

### unit-capability-map
最有价值的组合不是把某一项目整体搬入，而是把 OpenHands 的 typed client/skills seam、Goose 的 MCP/desktop/执行 seam、LangGraph 的 checkpoint/SDK、TaskWeaver 的 code/data history、Aider 的 coding UX 分别作为候选单位能力。

### ownership-risk
整体采用会同时继承候选的状态模型、权限模型、部署组件、升级节奏和安全假设；以自有产品语义为主、对单位能力做可移除适配，能把所有权责任限制在已验证的闭环。

### evidence-quality-axis
Stars 与 topicMatch 不能替代证据强度：Letta 的负面维护事实比高 Stars 更有决策价值，OpenCode/AutoGPT/Pydantic AI 的低证据应触发补采而不是乐观推断。

- 当前不推荐整体复用任何候选；推荐 C/D 混合：保留 qm-like 用户需求和产品语义为事实源，先补证据，再以单位能力选择性组合。
