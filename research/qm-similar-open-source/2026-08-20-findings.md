## 按方向的事实

### qm：产品锚点与证据边界

- 本轮 qm 的九条证据均落在 `AGENTS.md`，直接证明的是仓库维护、测试和工作约束，而不是完整产品功能；因此 qm 的产品形态以用户提供的项目定位为 benchmark，本轮 ledger 只把其维护表面作为可核验事实（Evidence `fda2e563d1e368c2bd37224d`、`921684cc00ec378acbe4f1dd`）。
- `unknownCriteria=0` 只表示每个候选/标准都有一条采集记录，不表示每项能力都被运行时证明；本轮必须把“有文件证据”和“闭环已验证”分开。

### 完整工作产品与执行 harness

- OpenHands 前端通过 typed client 访问 agent-server 的 conversation、event、git 和 skills 服务，并暴露 LLM/provider、settings、working directory 与 session API 配置（Evidence `2b92eeca52b2e775b2a34780`、`43e8740529cabcdd135c9d4f`、`d2c97e98509c1edaac30c7bc`）。
- OpenHands 证据还显示 public skills catalog、user/project skills、Cloud backend registry、device authorization、PostHog telemetry 和 lint/test/build CI；它更接近“可交付的 coding agent 产品面”，但本轮没有证明 qm 所需的组织级多 scope、Slack/web 同身份和后台工作语义（Evidence `35ffdb85c7fd2a2f4f9dcb4b`、`9a393669a76cf0f43d94ed6e`）。
- Goose 的仓库维护说明把它定义为 Rust agent framework，并同时维护 CLI 和 Electron desktop 接口；其 devcontainer、MCP integration test、issue board 和 clippy/test 规则证明它适合研究本地执行与扩展边界，但不证明多人共享工作空间（Evidence `8342519b6dec4afcbc860f79`、`c03f47ffca21e4aa5e7eded4`、`36f268b3e103c3d13a567993`、`ccca347bb938f98a1abd5fe3`）。
- Aider 的 README 明确把产品定位为与 LLM 结对编程，并支持云端和本地模型；它适合提取极简 coding UX 和 provider abstraction，不是 qm 的多人工作产品替代品（Evidence `0da05726323c81b5e77537ce`、`44f094d6daa8f438abb564ea`、`51d51a551d8d0349cee57dcf`）。

### 编排、状态与单位能力框架

- LangGraph 的仓库地图列出 stateful multi-actor agent、checkpoint、Postgres/SQLite checkpoint、CLI 以及 Python/TypeScript SDK；它适合作为 durable state、恢复和服务接口的单位能力参考，而不是直接的 Slack/web 工作产品（Evidence `1266c49589267df774dee5e9`、`06bfa6645b43d686af376096`、`bc964b8b7a425b0856ceaa62`）。
- CrewAI 的维护说明把项目定义为 Python agentic systems framework，并要求公共 API、复杂逻辑与 docs 一起维护；这支持其作为角色/任务编排单位能力参考，但本轮没有直接证明持久化 scope、沙箱和多人协作产品层（Evidence `71333c76e7055360b395d506`、`02b8e8d72aabd3c80fd5598d`）。
- AutoGen 的 README 证据与 Docker devcontainer 证据支持其作为 agent framework 和可复现开发环境参考；本轮没有从同一证据闭环推出 qm 的组织、身份和部署语义（Evidence `6867ddc092eda10b00bef823`、`75e442270a45d62febe84f32`、`576203d060741d1c914c50f1`）。
- AgentScope README 提供 docs、中文主页和 roadmap 入口；它是值得继续深读的 framework 候选，但本轮证据不足以证明它已经交付 qm 级别的 scope、sandbox 或运营控制面（Evidence `4f7686c3c463beb71b58e245`、`5c75d1ec2d5daa9cd67a023c`、`513f266b383c3d2bd87f5f8a`）。
- TaskWeaver 的 README 明确是 code-first agent framework，保留 chat history、code execution history 和 in-memory data，并以插件函数执行数据分析；它是“状态化代码执行 + 专业任务 UX”的清晰单位能力参考（Evidence `ed64a86a4fd96aefbdf38dcf`、`e0b7b37acf918229c4327b4e`）。

### 记忆、平台与负面证据

- Letta 当前 `main` 明确是 landing page；旧 V1 server、Docker image 和 Python server 已 retired，当前 harness、terminal UI、App Server、channels 和 runtime 位于 `letta-ai/letta-code`。因此不能把本仓库的 stars 或 archive 当作当前可复用实现（Evidence `548f48f69558fdef11bbf292`、`a4e9c9a6f76693d87213fc4f`、`3b19d68e1d4e0318e2a9b894`）。
- OpenCode、AutoGPT、Pydantic AI 的本轮证据主要落在翻译 glossary、前端维护规范或 CI reviewer 配置，没有足够的产品行为证据；它们应进入 `unverified/fog` 队列，而不能按 stars 排名后直接推断能力（Evidence `66a8a418bf2494cea4638124`、`0105594b9bd744c71b450a10`、`fa702490983b8750148dcfaa`）。

## 初步能力分层

| 方向 | 最值得深读 | 可先抽取的单位能力 | 暂不应直接继承 |
| --- | --- | --- | --- |
| 工作产品 | qm、OpenHands | scope-aware settings、skills catalog、typed client、device/cloud seam | 组织权限和后台工作闭环 |
| 执行 harness | Goose、Aider、OpenHands | provider abstraction、MCP/tool seam、coding UX、sandbox adapter | 完整多人协作数据模型 |
| 状态/编排 | LangGraph、AutoGen、CrewAI | checkpoint、state machine、delegation、SDK | 完整产品 UI 与身份系统 |
| 专业任务 | TaskWeaver | code/data history、plugin function、领域工作流 | 泛化为全能协作平台 |
| 记忆平台 | Letta（当前实现需转向 letta-code） | 仅作为待核验方向 | 直接复用 retired main/archive |
| 低证据候选 | OpenCode、AutoGPT、AgentScope、Pydantic AI | 先补 canonical README/docs/运行证据 | 依据 stars 或 topicMatch 直接选型 |

## 证据边界

本轮没有用“关键词未出现”证明能力不存在。尤其是 qm、OpenCode、AutoGPT、Pydantic AI 的证据质量不足；下一轮应按统一黑盒场景补采 README、核心状态模型、部署、安全与运行测试证据。`cline/cline` 与 `mem0ai/mem0` 因 GitHub tree 含当前 compiler 不支持的 `commit` 类型条目，本轮未进入 sealed ledger，需在采集器支持该树类型后补入同一比较矩阵。
