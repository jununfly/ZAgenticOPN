## 按主题的事实

### 产品边界与协作语义

- ZAgenticOPN 的设计把系统定义为窄职责 collaboration control plane，管理 private collaboration context、shared coordination facts 和 Work Item 生命周期，而不是通用记忆或完整工作流平台（Evidence `248dd286d0a5994e898f5fc5`）。
- ZAgenticOPN 明确把 Human、Device、AgentInstance、CollaborationScope、WorkItem 和 Claim 分开建模，并要求 Claim 表示 WorkItem 的唯一执行权（Evidence `8645d2d15464edc74469f69e`）。
- Routa 的 CLI 证据显示它暴露 workspace、session、task、ACP、specialist、Kanban、workflow、review、scan 和 team-coordination 能力；这使它成为 ext 中最接近完整交付协作表面的候选，但该证据尚未证明它与本项目的 Human-triggered pull 语义一致（Evidence `805bad2827279015d5b4ceca`）。
- MCP Agent Mail 的 conformance 文档记录了 Python 行为 fixtures、Rust 扩展工具和工具过滤/错误 envelope/outage 检查；它更像可嵌入的 Agent 间消息与工具协作层，不能仅凭该证据认定为 Work Item frontier 控制面（Evidence `ead655695e25e977e1f69c74`, `20ede320af29f9d9408aafc7`）。
- Avernet 的架构规则强调 contracts、dependency direction、plugin behavior、configuration-driven assembly 和 change control；这是可维护基础设施的证据，不等于已公开完整的协作任务语义（Evidence `fbf02a7c1a5b401e41e20f80`, `0b02c9150e6d41270d5ca596`）。

### 上下文、事实源与边界

- ZAgenticOPN 要求 Agent 显式 publish 才能把 private observation 变为 shared fact；shared context 保存摘要与引用，Git 仍拥有代码、Spec、Plan、commit 和测试事实（Evidence `5b5e5fc70b277763c2584295`）。
- qm 的 deployment CLI 将 security guarantees、target behavior、lifecycle 和 agent-consumable package runbook 放入 deployment repository，说明它把部署配置与 Agent 可读操作约定作为一等交付面（Evidence `83f71d8234a3ba87d34ae162`）。但本轮证据没有直接证明 qm 的 shared context 是否提供 C1–C4 所需的发布、frontier、唯一 claim 和跨 Agent review。
- ZAgenticLoop 的 Quickstart 规定第一周只 report、不 auto-fix 或 auto-merge，并将 readiness audit 与 Route Table 作为执行前控制面；它体现了可复用的治理思想，但也与当前“先走通体验闭环、后按失败加固”的阶段纪律存在张力（Evidence `05857a65672ee68383f51551`, `7fc62bc4ac780e8901a16e02`）。

### 多设备运行与集成

- ZAgenticOPN 的设计将 Agent integration、Coordination service、Coordination store 和 Markdown scorecard 分开，并通过领域操作连接 heterogeneous Agents 与 Git（Evidence `9c5489915f28cd3f04c077dd`）。
- qm 的 CLI 文档说明部署目录承载规范、安全和生命周期，并提供独立部署 CLI；它是 ref 类中较强的 deployment/product shape 参照，但是否适合作为 base 的运行时仍需 conformance 实验（Evidence `8f64ff6b548597119cd1db1f`）。
- ZAgenticLoop 已发布 loop-sync、MCP server、goal-audit 等独立包；这证明其有可安装的跨项目工具表面，但不能证明首个体验版已经完成（Evidence `5f2c1a432b852dd040ff6ea2`）。
- Routa 的 package 与 CLI 证据显示存在桌面运行面，以及 workspace/session/task/Kanban/workflow/review/team-coordination CLI 表面；这提高了其跨设备与集成潜力，也带来双后端和较大的组合责任（Evidence `71f6367891ce9960ff4e8871`, `805bad2827279015d5b4ceca`）。
- Avernet 的 Bot Provider 文档以 HTTP webhook、`chat.history` 和 `bot.ping` 定义外部 bot 接入与健康探针，并提供 minimal integration flow；它适合研究异构 runtime 接入，但公开接口仍需核实 shared Work Item 语义（Evidence `db8183b3d9de1f31bec8e770`, `ca9a3a82a5604fdf09982d03`, `8edb277026b066ece09322cc`）。

### 维护、验证与运行风险

- ZAgenticOPN 把 product code、PoC、deployment 和 ZAgenticLoop code extraction 都置于 open-source comparison gate 之后；这是 base 项目的当前准入规则（Evidence `3d573bbf7985150a5102a7f8`）。
- ZAgenticLoop 的 Quickstart、readiness audit 和 release package 证明它有较强的维护与治理表面；其历史开发失败使它适合作为 legacy 参照，不适合作为当前新项目的默认架构继承源（Evidence `9acb07dda4c0d758ae37d1ad`, `7fc62bc4ac780e8901a16e02`, `5f2c1a432b852dd040ff6ea2`）。
- Avernet 的公开架构规则要求契约变化配套文档、兼容性审查和 conformance tests；这对长期维护有价值，但不应把治理成熟度直接换算为首个 Experience Version 的产品拟合度（Evidence `526c6161733e9cf47f90bb49`, `8058044f682d749c016128f8`）。
- MCP Agent Mail 的 conformance 文档包含 docs drift、工具过滤、错误 envelope 和 outage 检查；这类验证能力可作为单位能力候选，但项目的 advisory reservation 与消息模型需要单独映射到 Work Item claim（Evidence `913ec4235f3b383b910e665d`, `1542c4d2630a7205854408e`, `9d7d24ec907881282ab7816d`）。

## 证据边界

本轮没有用“未出现关键词”证明某能力不存在。特别是 qm、Routa、MCP Agent Mail 和 Avernet 的本轮 evidence 主要覆盖文档、CLI、架构规则或 conformance 表面；C1–C4 的原子 claim、跨 Agent review 接续、Human-triggered pull 语义仍需黑盒 conformance 验证。
