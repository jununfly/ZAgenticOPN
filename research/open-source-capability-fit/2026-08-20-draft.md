# ZAgenticOPN 的开源能力拟合与 merge 目标分析

## 1. Executive summary
建议把 ZAgenticOPN 保持为 base 和最终 merge 目标，采用 C 类的 base-led selective reuse：吸收经过 conformance 验证的单位能力，不直接把任何 ref、legacy 或 ext 项目当作产品架构。qm 是当前最有价值的 ref，产品形态和部署控制面值得重点对比，但本轮 sealed evidence 尚未证明 C1–C4 协作闭环；Routa 是最值得优先验证的 ext，MCP Agent Mail 适合作为消息、预留和审计单位能力参考，Avernet 更偏分布式协作网络。ZAgenticLoop 保持 legacy，不迁移代码。

- 当前推荐 C：以 ZAgenticOPN 为 base-led architecture，选择性吸收 qm、ZAgenticLoop 或 ext 项目中通过 C1-C4 与 R5/R6/R8 conformance 的单位能力；不直接采用任何候选作为整体产品架构。
- 把 qm 作为第一优先 ref：先做一次针对根 README、核心状态模型、共享 scope、claim/review、部署和 sandbox 的定向证据补采，再运行同一 C1-C4 与 R5/R6/R8 黑盒场景；通过后优先评估 B1 adapter 或 C 类 selective reuse。
- 把 Routa 作为第一优先 ext conformance 候选，因为其公开 surface 最接近 workspace/task/review/team coordination；先验证 claim、frontier、跨 Agent review 和 Human-triggered pull，再评估其是否带来非线性平台责任。
- 将 MCP Agent Mail 限定为消息、reservation、conformance fixture、错误与 outage 处理的候选单位能力；不要把消息线程直接当作 Work Item 状态机。
- ZAgenticLoop 保持 legacy，不继续开发，不建立运行时依赖，也不预先抽取代码；只有当前 Experience Version 的具体失败证明某个单位能力值得抽取时，才重新评估该能力。
- 保持 ZAgenticOPN 的 private/shared context、Work Item、唯一 Claim、review continuation、Git provenance 和 lifecycle gate 为事实源；候选项目只能通过证据矩阵进入 base，不能反向改写产品目标。

## 2. Key findings
- ZAgenticOPN 把产品边界定义为窄职责 collaboration control plane，管理 private collaboration context、shared coordination facts 和 Work Item 生命周期。 [[1]](https://github.com/jununfly/ZAgenticOPN/blob/75cf819a73c35b9cd821b294ea17c832b70cf6b6/docs/designs/agent-self-service-collaboration.md)
- ZAgenticOPN 把 Agent private context、shared fact 和 canonical Git fact 分层，并要求显式 publish 才能把私有观察升级为共享事实。 [[2]](https://github.com/jununfly/ZAgenticOPN/blob/75cf819a73c35b9cd821b294ea17c832b70cf6b6/docs/designs/agent-self-service-collaboration.md) [[3]](https://github.com/jununfly/ZAgenticOPN/blob/75cf819a73c35b9cd821b294ea17c832b70cf6b6/docs/designs/agent-self-service-collaboration.md)
- ZAgenticOPN 当前公开快照提供 Product Spec、candidate-neutral design 和 roadmap 文档入口；本报告不把这些文档入口解释为已有运行时实现或可直接复用的产品。 [[4]](https://github.com/jununfly/ZAgenticOPN/blob/75cf819a73c35b9cd821b294ea17c832b70cf6b6/README.md)
- qm 的部署 CLI 将部署目录中的 security guarantees、target behavior、lifecycle 和 agent-consumable package runbook 作为规范化交付面。 [[5]](https://github.com/yc-software/qm/blob/568252bd4e6da5288b239573abef972f3e16b3f9/cli/README.md) [[8]](https://github.com/yc-software/qm/blob/568252bd4e6da5288b239573abef972f3e16b3f9/cli/README.md)
- 本轮 sealed evidence 尚未证明 qm 已覆盖 Human-triggered publish → discover → unique claim → result → Agent review continuation 的 C1-C4 闭环；该结论是 unverified，不是 absent。 [[6]](https://github.com/yc-software/qm/blob/568252bd4e6da5288b239573abef972f3e16b3f9/cli/README.md) [[7]](https://github.com/yc-software/qm/blob/568252bd4e6da5288b239573abef972f3e16b3f9/cli/README.md) [[9]](https://github.com/yc-software/qm/blob/568252bd4e6da5288b239573abef972f3e16b3f9/cli/README.md)

- ZAgenticLoop 已有可发布的 loop-sync、MCP server 和 goal-audit package 表面，但这些事实不证明首个体验版完成，也不构成 ZAgenticOPN 的默认依赖。 [[14]](https://github.com/jununfly/ZAgenticLoop/blob/c80f590a9867558cbc8d338cf7d712ddc9c5204e/docs/RELEASE.md) [[12]](https://github.com/jununfly/ZAgenticLoop/blob/c80f590a9867558cbc8d338cf7d712ddc9c5204e/docs/QUICKSTART.md)

## 3. Analysis & synthesis
### fit-model
应先用 C1-C4 与 R5/R6/R8 作为关键闭环淘汰门，再用功能覆盖、语义匹配和可组合性计算有效拟合度；不能用 Stars、功能数量或 README 丰富度替代闭环证据。

### role-comparison
ZAgenticOPN 是最终语义和 merge 目标；qm 是产品形态与部署控制面 ref；ZAgenticLoop 是 legacy 经验来源；Routa、MCP Agent Mail、Avernet 是不同方向的 ext 候选。角色不同，不能放在同一“谁最好”排序里。

### capability-comparison
Routa 的交付协作 surface 最接近 C1-C4，qm 的产品形态和 deployment/control surface 最值得作为 ref，MCP Agent Mail 的消息与 reservation 单位能力最清晰，Avernet 的异构网络接入最突出；但当前没有任何 ref/ext 证据足以取代 ZAgenticOPN 的 base 语义。

### ownership-comparison
直接采用任何候选都会把其未验证的状态语义、数据模型、部署方式和升级责任引入 base。更稳妥的路径是让 ZAgenticOPN 保有核心状态机和验收协议，只对通过黑盒 conformance 的单位能力做选择性 merge。

### 3.7 Recommendation
- 当前推荐 C：以 ZAgenticOPN 为 base-led architecture，选择性吸收 qm、ZAgenticLoop 或 ext 项目中通过 C1-C4 与 R5/R6/R8 conformance 的单位能力；不直接采用任何候选作为整体产品架构。
